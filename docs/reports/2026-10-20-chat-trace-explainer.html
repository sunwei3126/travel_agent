02 · Request lifecycle

一次发送，如何变成屏幕上的折叠块

先看“首次发送”。这里最容易误解的是：前端并没有直接调用 Fastify； 它调用 Next 的 per-trip CopilotKit runtime，运行时再把 AG-UI 请求转给 /agui。切换下面的场景，观察每条路径。

发送 / 工具 / 恢复：三条路径 实线 = 实时；虚线 = 查询

首次发送：agent/run 进入 Next runtime，HttpAgent 调 Fastify /agui；Fastify 先挂 watcher 再提交消息，随后写 RUN_STARTED、两个快照和实时事件。

记住两个边界：Next 运行时是无状态桥，它按 trip 构造 HttpAgent； Fastify 的 /agui 是唯一启动 run 的地方，它先挂 watcher、再提交消息， 这样 run_start 和 run_end 都不会丢。快照里的用户消息由 pending-user-<runId> 补上，避免 MESSAGES_SNAPSHOT 覆盖刚发送的消息。

03 · Design insights

这套实现真正值得学的地方

下面七条不是“最佳实践”清单，而是这个系统在真实运行中被迫形成的选择。 每条都对应一个具体的失败模式。

  1. durable doc 是状态，事件流只是投影

    brief、plan、sources、research 计数都是 pi-durable 文档；重启、崩溃、刷新后都能恢复。事件流可以断，状态不能丢。所有“刷新后还在”的能力都来自这里。

  2. mapper 是有状态的投影器，不是无脑转发

    pi 事件是增量的、provider-specific 的；AG-UI 要求严格的 span 生命周期。mapper 必须记住已发送文本、reasoning span、tool call 状态，并在 run_end 前关闭所有实体，否则 verifyEvents 会拒绝 RUN_FINISHED。

  3. 工具参数有两条生命周期，别混在一起

    模型流里的 toolcall_delta 是 path + 值片段，不是 JSON；执行阶段的 tool_execution_start.args 才是权威对象。正确做法是：只发一次权威 JSON，TOOL_CALL_END 等执行开始或 run_end。

  4. message_end 会回放整条消息

    它带着完整的 assistant content 再次出现。已经流式发过的 thinking 块不能再发一遍；重开 span 时必须携带已发送长度，只补后缀。否则用户会在回答下方看到完整的思考过程第二次出现。

  5. 文本要懒启动，思考才能排在前面

    空的 message_start 不发 TEXT_MESSAGE_START；首个文本内容或结束时才发。这样既不会出现空助手气泡，也能让 reasoning 块自然地排在文本之前。

  6. UI 同时消费实时状态与 durable 快照

    聊天消息来自 CopilotKit 的实时事件；计划卡来自 useTripSnapshot 的 2 秒轮询。两者都用“最新 day card 的 updatedAt”比较新旧，而不是盲信任何一边。

  7. 每个 trip 一个 conversation，工具任务也 durable

    研究、抓取、草图都是 durable task。生成任务失败会 park，工具任务失败不会结束 run；faults 和 travel.task_failed 把这两种情况分开呈现。崩溃恢复测试专门验证这条边界。

一条经验

当“实时”和“durable”同时存在时，先问：谁是记录，谁是视图？ 这个系统里，pi-durable 的 transcript 是记录；CopilotKit 的消息、计划卡、研究计数都是视图。 任何视图都可以重建，任何记录都不应该被视图覆盖。

深入：为什么 Next 运行时里要做一次结构性 cast？

@copilotkit/runtime 与 @copilotkit/shared 各自打包了一份 @ag-ui/client。两边的 HttpAgent 类带有私有字段 _debug， 在 TypeScript 里是名义不兼容的，但运行时结构完全一致。于是 route 里用 as unknown as ConstructorParameters<typeof CopilotRuntime>[0] 只放宽这一处边界；升级依赖时应该优先消掉这个 cast，而不是继续扩散。

05 · Failure modes

三个坑位，三段真实事件

这三处都曾经在真实流里出现，并且都有对应的回归测试。 切换标签看“症状 → 根因 → 现在的规则”。

症状：回答下方又出现一遍完整思考

模型流结束后，message_end 回放完整 assistant content。 如果文本或工具调用已经把 reasoning span 关闭，旧的实现会新建一个 span 并把整段 thinking 再发一次。

  1. thinking_start / thinking_delta → REASONING_MESSAGE_START / CONTENT（“先想一下”）
  2. text_start → 关闭 reasoning，REASONING_MESSAGE_END / REASONING_END
  3. message_end → 旧实现：新建 span，再发一次“先想一下”
  4. reasoningCovered() → 已发送长度 ≥ 回放文本，直接跳过；重开 span 时携带 emitted，只补后缀

规则：同一个 contentIndex 的 thinking 块，已发送的内容永远不再发。空的 thinking 块不要新开 span。

症状：实时参数是 {}、片段或错误 JSON

部分 message_start / snapshot 已经带了一个 toolCall block，但参数还不完整； toolcall_delta 带的是 path + 值片段（例如 " 门票"），不是 JSON。

  1. message_start → 旧实现：TOOL_CALL_ARGS "{}" + TOOL_CALL_END（过早）
  2. toolcall_delta → 旧实现：把值片段直接拼到 JSON 字符串，得到非法参数
  3. message_end → 权威 block.arguments：只发一次完整 JSON
  4. tool_execution_start → 参数已发则只发 TOOL_CALL_END；未发则补发 ARGS + END
  5. tool_execution_end → TOOL_CALL_RESULT + metadata["travel.tool"]（name / status / error / duration）

规则：只发权威 JSON；END 等执行开始或 run_end；END 之后绝不再发 ARGS。

症状：刷新后聊天空白，但计划卡还在更新

CopilotKit 连接瞬间会短暂暴露 1 条空 assistant 消息。旧的历史加载守卫是 messages.length > 0，于是它把“占位消息”误判成“已有真实对话”， 再也不去取 transcript。

  1. mount isAvailable=false → 不取历史
  2. isAvailable=true messages = [1 条空 assistant] → 旧守卫直接 return
  3. hasRenderableHistory() 只有 user / reasoning / 有内容的 assistant / tool 才算真实对话
  4. Promise.all getTranscript + getTrip；running 时每 2 秒轮询，结束后重取

规则：判“有没有对话”要看可渲染内容，不要看数组长度；刷新发生在 run 中途时，要等 run 结束再补一次 transcript。

还有两个运行时坑

“Cannot use a settled overlay”

不要从 api.commit() 里拿到 draft 后在 commit 外读取。搜索工具现在在 commit 内返回普通副本，并在提交后用新快照构造输出；真实 Harness/SQLite 集成测试覆盖了这条路径。

重启 API 后的首次发送

重启 Fastify 后，Next dev 进程可能还握着旧的 keep-alive 连接，首次 agent/run 会立刻结束。重启 API 时一并重启 Next dev，或先发一条短消息预热；这不是业务逻辑错误。

07 · Start here

开始工作的最小路径

跑起来 → 看一条真实运行 → 改一个小工具 → 跑验收。 不要一开始就读 mapper 的全部 700 行；先看测试里的输入/输出形状。

启动

export DEEPSEEK_API_KEY=...
npm install
npm run dev                      # Fastify :4000
npm run dev --workspace @pi-demo/web   # Next :3000

默认走本地 magpie（http://127.0.0.1:3425，模型 deepseek/deepseek-flash）。PI_THINKING_LEVEL=low 会开启思考；设为 off 可关闭。若 magpie 不可用，可用 MAGPIE_BASE_URL / MAGPIE_MODEL / MAGPIE_API_KEY / MAGPIE_MAX_TOKENS 指向远端 Anthropic-compatible 端点。

测试与验收

npm test                                  # server + web + shared
npx tsc -p apps/server
npm run build --workspace @pi-demo/web
npm run probe:thinking                    # magpie 是否真的返回 thinking
npm run acceptance:live                   # 15 分钟真实场景
npm run acceptance:crash                  # SIGKILL 后恢复

改一个工具时

  1. 定义：在 apps/server/src/agent/tools/ 用 defineTool 定义参数、执行和 replay 语义。
  2. 注册：在 extension 里注册；更新系统提示，写清楚什么时候调用。
  3. 输出：需要模型消费的内容放 output；需要 UI 消费的结构放 structuredOutput。
  4. durable：在 api.commit() 内完成读写；不要带 draft 出 commit。
  5. 测试：加工具单测 + 一次真实 Harness/SQLite 集成测试；如果会发事件，补 mapper 测试和 verifyEvents。

改事件映射时

  1. 先写一个 mapper 单测，构造真实 pi-durable 形状（changes、block、message_end、tool_execution_*）。
  2. 如果新增/改变生命周期，更新 mapper.protocol.test.ts，让整段事件通过 verifyEvents。
  3. 确保 run_end 能关闭所有 reasoning / text / tool 实体；否则 RUN_FINISHED 会被拒绝。
  4. 如果改变 UI 可见内容，更新 lib/chat.test.ts 和 ChatPanel.test.tsx。
阅读顺序建议

先读 packages/shared/src/trip.ts 建立数据形状 → harness/transcript.ts 看历史怎么来 → agui/mapper.ts 只看测试覆盖的 case → lib/chat.ts 看 UI 怎么分组 → ChatPanel.tsx 看发送/历史/滚动。最后再读 service.ts 的 durable 细节。

术语表

术语在这里的含义
Conversation一个 trip 对应一个 pi-durable conversation；重启后仍存在。
Run一次用户提交触发的生成周期；以 run_start / run_end 为边界。
Taskdurable 的后台工作单元；生成任务失败会 park，工具任务失败不结束 run。
Entry / Transcriptpi-durable 的提交记录；转换为共享 TranscriptEntry 后用于历史和快照。
