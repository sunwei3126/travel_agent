# 旅游规划智能体设计（泰山首测）

日期：2026-10-19
状态：设计待评审

## 1. 意图与背景

做一个自己真的会用的旅游规划工具，不是技术演示。

用户用一段自然语言描述出行需求，agent 先补全关键信息，再用 DeepSeek 的搜索与抓取接口做研究，最终在 CopilotKit 聊天界面里给出图文并茂的按天行程。每天一张卡片，配一张模型现场画的 SVG 草图。整套对话、研究资料和方案都持久化：下次回来可以接着聊，进程崩溃或重启后也能恢复。

第一次真实验收行程：泰山 3 天，2026-10-26 从上海虹桥火车站出发，独自，预算 ¥3000，体力一般，在意风景和美食。

## 2. 核心体验

1. 用户新建一次旅行，输入一段需求。
2. agent 检查关键信息是否齐全：目的地、出发地、日期与天数、预算、同行人、体力、偏好。缺什么就问什么，一次少量关键问题；信息不齐不开始研究。
3. 信息齐全后进入研究阶段。界面显示正在搜什么、抓了哪些页面、拿到多少来源。
4. 研究完成，方案以聊天流里的“一天一卡”出现：当天标题、时间安排、风景与美食取舍、交通、预估花费、来源链接，以及一张模型生成的 SVG 草图。
5. 用户继续对话修改，例如“第三天轻松一点”“换成亲子路线”。只更新受影响的那一天卡片。
6. 关掉页面、刷新、重启服务甚至崩溃后再回来：会话、研究资料、方案卡片都还在，可以继续。

## 3. 首测验收场景

输入：

> 泰山玩三天，2026-10-26 从上海虹桥火车站出发，自己去，预算 3000，体力一般，在意风景和美食。

方案至少要回答：

- 10 月 26 日从虹桥到泰安的交通方式与时间，返程安排。
- 住哪一带，为什么。
- 三天怎么分，徒步与索道怎么组合才适合体力一般的人。
- 看日出是否值得、要不要住山顶，以及十月底的天气与装备提示。
- 岱庙、山下和山上的美食怎么穿插。
- 总花费分项估算，且不超过 ¥3000。
- 每条关键结论带来源；无法核实的标注为未核实。

## 4. 目标

- 产出一份用户愿意照着走的泰山三日方案。
- 关键事实有来源，价格与营业时间标明时效。
- 刷新、重启、崩溃后不丢已提交的对话、研究和方案。
- SVG 草图稳定渲染；画坏了有重试或占位，不破坏界面。
- 修改某一天时，不重复研究整趟行程。

## 5. 非目标

- 不做订票、订酒店、支付。
- 不保证价格实时或可订，只给搜索到的估算。
- 不做地图导航、离线地图、实时天气推送。
- 不做多人协作、账号体系、云端部署；单机本地运行。
- 不做图片搜索或照片；视觉只用 SVG 草图。
- 不做通用搜索引擎；搜索只服务旅行研究。

## 6. 失败条件（即使功能跑通也算失败）

- 编造事实、价格、营业时间，或把过期信息当现状。
- 方案忽略“风景和美食”“体力一般”“预算 3000”这些 constraint，给一份通用攻略。
- 追问过多，或信息不齐就开始研究。
- 崩溃后丢状态；已完成的搜索/抓取被重复执行或重复计费（在途请求可能重复一次，见 9.12）。
- SVG 畸形、溢出、带脚本，或渲染失败后界面不可用。
- 用户改一天，结果整份方案被重做，已确认的内容丢失。

## 7. 约束

- 单用户、本地 Windows 11，中文界面与中文内容。
- Node.js 22.22.1（pi-durable 要求 ≥22.19.0）。
- pi-durable `@earendil-works/pi-durable` 1.3.0，实验性，API 可能随版本变化。
- 持久化用 SQLite 单文件；同一时间只能有一个进程打开。
- 模型走本机 magpie 网关 `http://127.0.0.1:3425`，Anthropic Messages 格式。
- 搜索走 DeepSeek 官方 Search/Fetch API：
  - `POST https://api.deepseek.com/v1/tools/search`
  - `POST https://api.deepseek.com/v1/tools/fetch`
  - Bearer 认证；key 从环境变量或本地配置读取，不写死。
  - Search 每账号 5 QPS，Fetch 每账号 5 QPS；仅成功请求计费，¥5/千次。
- 前端 CopilotKit 1.79.1，AG-UI 客户端 1.0.3。

## 8. 已定的选择（用户决定）

- 后端使用最新的 pi-durable 库，不是 Pi CLI 的 session 扩展。
- 前端使用 CopilotKit。
- 模型访问走本地 magpie 网关，Anthropic Messages 格式。
- 搜索使用 DeepSeek 最新的 Search/Fetch 接口。
- “图”是模型直接生成的 SVG 代码。
- 界面以聊天流为主，方案按“一天一卡”出现。
- 信息不全时先问关键问题，信息完整后再规划。
- 非目标按第 5 节执行。

## 9. 实现决策（我们的判断，可被实现者调整细节）

### 9.1 总体架构

- `web/`：Next.js App Router + React + CopilotKit，负责聊天界面、按天卡片、行程列表、SVG 展示。
- `server/`：Node.js + TypeScript 服务，负责：
  - pi-durable harness 与 SQLite 持久化；
  - DeepSeek Search/Fetch 工具；
  - magpie 模型接入；
  - AG-UI 桥接端点。
- 两者通过 AG-UI 通信。前端不接触任何密钥。
- 本地开发时两个进程分别启动；服务只监听 `127.0.0.1`。

### 9.2 pi-durable 接入

- 持久化：`openNodeSqliteStorage("./data/pi.sqlite")`，WAL 模式；数据目录不进版本库。
- 启动时 `Harness.open(...)` 后调用 `harness.resume()`，续跑上次未完成的任务。
- 每次旅行一个 conversation（`ownership: ownerless`）。行程索引单独维护一份小型本地索引（JSON 或宿主表），记录 tripId、conversationId、标题、目的地、日期、更新时间、状态。
- 自定义文档：
  - `trip.brief`：出发地、目的地、日期、天数、预算、同行人、体力、偏好、约束、是否完整。
  - `trip.plan`：按天卡片数组，含标题、时间块、风景/美食、交通、预估花费、来源 id、SVG、SVG 状态、更新时间。
  - `trip.sources`：来源缓存，含 id、查询、标题、URL、摘要、正文引用、日期、authority、rerank_score、抓取时间。
- 工具用 `defineTool`，扩展用 `defineExtension`。只读的搜索/抓取/建模工具声明 `replay: "safe"`，并做查询缓存，避免崩溃重放造成重复计费。
- 忽略非必要能力：不使用 code mode、不使用 subagent，首版保持单 agent。

### 9.3 澄清阶段

- agent 维护 `trip.brief`，必填项：目的地、出发地、日期、天数、预算、同行人、体力、偏好。
- 缺项时用普通聊天消息提问；每轮最多问 3 个关键问题。
- `plan_emit_day` 工具在 `trip.brief` 不完整时拒绝写入，作为硬性 guard。
- 用户补充信息后，用 `trip_update_brief` 工具更新文档；不要默默假设。
- 可以给合理默认值，但必须说出来并写进 brief，例如“默认住泰安市区，不行我再改”。

### 9.4 研究阶段

- `deepseek_search`：参数为 query、count、ori_question、need_content、localization；返回结构化结果，写入 `trip.sources`。
  - 优先 `authority >= 3` 且 `rerank_score >= 1.5` 的结果。
  - 查询支持 `site:`、`after:`、`before:`、`lang:` 等操作符。
  - 缓存键为规范化后的 query + 参数，命中则不再请求。
- `deepseek_fetch`：按 URL 抓取正文，写入来源缓存；正文截断后给模型，完整内容留在文档里。
- 研究预算：每趟最多 40 次 search、30 次 fetch；同 URL 只抓一次；严格遵守 5 QPS。
- 关键结论必须带来源 id；找不到来源时明确标注“未核实”，不得编造。
- 每完成一部分研究就把来源和结论提交到文档，崩溃后不用从头再来。

### 9.5 方案与 SVG

- `plan_emit_day`：写入或替换某一天的卡片，按 day index 幂等。写入前校验：brief 完整、来源 id 存在、预估花费字段存在。
- `sketch_day`：把当天摘要交给同一个模型，要求只输出 SVG；服务端校验后存入该天卡片。
  - 校验：可解析为 XML；根元素是 `<svg>`；存在 viewBox；尺寸在 1200×800 内；去掉 `<script>`、`<foreignObject>`、`on*` 事件属性、外部 `href`、外部 `<image>`、CSS 外链。
  - 不合格：带错误信息重试一次；仍失败则用确定性占位图，并在卡片上提供“重画”操作。
- 前端用 `<img src="data:image/svg+xml;base64,...">` 渲染，避免 SVG 内的脚本执行。
- 草图风格：手绘感、有限配色、少量文字；重点表达地形、路线或当天主题，不追求写实。
- 费用：每张卡片给分项区间；`plan_finalize` 汇总并与预算比较，超预算时标红并给出削减建议。

### 9.6 AG-UI 桥

- 后端暴露每趟会话的 AG-UI 流（SSE）。连接时用 `watchEvents()` 的 snapshot 初始化，随后按提交批次推送事件。
- 事件映射：
  - 运行生命周期 → `RUN_STARTED` / `RUN_FINISHED` / `RUN_ERROR`。
  - 助手文本增量 → `TEXT_MESSAGE_START/CONTENT/END`。
  - 工具调用与结果 → `TOOL_CALL_START/ARGS/END/RESULT`。
  - `trip.brief`、`trip.plan`、`trip.sources` → `STATE_SNAPSHOT` / `STATE_DELTA`。
- pi-durable 的事件流不能按游标续传，所以断线重连一律重新发 snapshot，再由前端合并。
- 用户输入通过 `conversation.submit({ type: "input", content, requestId })` 写入；requestId 由客户端生成，重试幂等。
- 默认作为 follow-up 排队；修改类消息可用 steer，让当前工具轮结束后加入。

### 9.7 前端界面

- CopilotKit 聊天为主界面，支持自定义渲染。
- 按天卡片由 `trip.plan` 状态驱动，不依赖某条临时工具消息；断线重连后仍能重建。
- 卡片内容：天标题与日期、SVG 草图、时间块、风景与美食推荐、交通、预估花费、来源 chips、“改这一天”快捷操作。
- 信息不完整时显示 brief 缺项清单；研究阶段显示搜索/抓取进度与已收集来源数。
- 左侧或抽屉式行程列表：目的地、日期、更新时间、状态；点开即恢复。
- 首版只做桌面宽屏，移动端可用即可。

### 9.8 模型接入（magpie）

- 用 pi-ai 的 `createProvider()` 定义一个 `magpie` provider：
  - `api: anthropicMessagesApi()`（`@earendil-works/pi-ai/api/anthropic-messages.lazy`）。
  - `baseUrl: "http://127.0.0.1:3425"`。
  - key 用固定占位值即可（magpie 接受任意本地 key），不要读取并转发真实上游密钥。
- 模型 id 通过 `/v1/models` 选择，默认 `openrouter/deepseek/deepseek-v4.1-flash-1017`（1,048,576 上下文）；用环境变量 `MAGPIE_MODEL` 覆盖。
- 规划与 SVG 生成默认用同一个模型；后续可按任务拆模型。
- 思考等级通过模型配置传入，默认中等；失败时记录并降级。

### 9.9 错误处理与恢复

- 网络错误指数退避重试；DeepSeek 429 遵守 Retry-After，并降低并发。
- 搜索全部失败：告诉用户失败原因，保留已完成部分，提供重试；不得用模型记忆硬编方案。
- SVG 两次失败：占位图 + 重画按钮。
- 超预算：卡片与汇总标红，给出具体削减项。
- pi-durable 的 `onReport` 记录 task fault/parked；界面能显示“任务已暂停”并提供重试。
- 服务重启：先 `resume()`，再接受新请求；正在生成的回答从最近检查点续跑。

### 9.10 安全与本地性

- 服务只绑 `127.0.0.1`；首版不做登录，因为只有本机单用户。
- DeepSeek 与模型密钥只存在服务端环境变量/本地配置里。
- SVG 服务端清洗 + 前端图片化渲染。
- 不把用户输入当作任意 URL 去抓取；Fetch 只用于搜索结果给出的 URL。
- SQLite 数据目录加入 `.gitignore`。

### 9.11 成本与速率

- DeepSeek Search/Fetch：按成功请求计费；用缓存、去重和查询上限控制成本。
- 模型调用：由 magpie 统一计费；记录每趟 token 用量（pi-durable 自带 usage 文档）。
- 首版目标：一趟泰山规划的研究调用控制在 40 次 search + 30 次 fetch 以内。

### 9.12 评审后补定的规则

**来源与时效**

- 搜索 snippet 只当线索；价格、营业时间、交通班次等硬事实必须抓取原页面后才算核实。
- 来源优先级：官方（景区、铁路、政府文旅）> OTA（携程、美团等）> 博客与论坛。
- 价格与营业时间：优先使用 90 天内的来源；更旧的来源标注“可能过期”，并继续寻找新来源。
- 交通班次：以 12306 / 铁路官方为准；搜索到的时刻表标注“以 12306 实际查询为准”，不作为可执行承诺。
- 十月底天气：只使用气候常年值或临近 7 天内的预报，并明确标注类型，不把常年值写成当天预报。

**预算口径**

- ¥3000 是整趟总预算：往返高铁、当地交通、两晚住宿、门票、索道、餐饮和机动费用。
- 每张卡片给区间；`plan_finalize` 用各区间上界求和做通过判定，超过即标红并给削减建议。界面同时展示区间与总额。

**引用粒度**

- 关键结论按 claim 级引用：每条价格、时间、班次、路线结论都要有自己的 `sourceIds`。
- 主观推荐可以引用来源，也可以标为“agent 判断”，但不得伪装成事实。
- `plan_emit_day` 校验：硬事实 claim 必须有存在的来源 id；没有来源的必须逐条标“未核实”。
- 卡片可以有主观建议，但硬事实零来源的卡片不允许写入。

**外部数据源**

- 首版只用 DeepSeek Search/Fetch，不接 12306、天气或其他专用 API。
- 因此交通与天气结论必须带来源和时效标注；搜索不足时明确告诉用户，而不是凭记忆补全。

**重复计费边界**

- 已完成的 search/fetch 通过缓存永不重复；崩溃或断电后，结果已返回但尚未落盘的“在途请求”可能重复一次。
- 这是 at-most-once（完成后不再发），不是 exactly-once；验收 C 按此口径断言。
- 每次请求前记录 attempt 意图，结果提交后标记完成；重启时只重试未完成的 attempt。

**编辑范围**

- 点名某天的修改只改那天；预算、日期、住宿、交通等跨天修改，直接级联更新所有受影响的天。
- 更新后在被改动的卡片上标注“已更新”，并在聊天里用一句话说明影响了哪几天。
- 不设“锁定”机制；所有卡片都是当前状态。用户明确说“某天不要动”时，该天不参与级联。

## 10. 验收与测试

- A. 完整 brief：直接进入研究，产出 3 张按天卡片，含 SVG、来源、费用分项；各区间上界之和 ≤ ¥3000。
- B. 不完整 brief：先提问；补齐前不出现任何 `plan_emit_day` 写入。
- C. 崩溃恢复：在研究中途杀掉服务进程，重启后会话继续，已完成的搜索/抓取不重复执行；在途请求最多重复一次（at-most-once）。
- D. 刷新恢复：浏览器刷新或断线重连后，从 snapshot 重建聊天与卡片。
- E. SVG 失败：注入非法 SVG，验证重试与占位图，界面保持可用。
- F. 局部修改：要求“第三天轻松一点”，只有 Day 3 卡片变化。
- G. 引用：每条价格、时间、班次、路线等硬事实 claim 都有来源 id；无来源的逐条标注未核实。
- H. 内容：首测方案覆盖虹桥往返、住宿区域、徒步/索道组合、日出决策、美食、预算分项。
